# /kickoff - 从想法到自主循环开发（Nova 前门编排器）

从一个想法启动一次完整的特性开发：**调研需求 → 拆解任务台账 → 起飞自主循环**。
每个产出都有人工门，你点头才往下——**前段你把关「做什么」，后段交给 `/dev-loop` 自主做「怎么做」**。

> **关键节奏**：前段（需求 + 任务拆解）**只产文档、绝不碰代码**；代码实现等到 `/dev-loop` 阶段才做。
> 🔴 全程严守 AGENTS.md 中的架构红线：PTY 直通不拦截、凭据走 Keychain、axum 仅 127.0.0.1。

## 用法

```
/kickoff <一句话特性想法>
```
例：`/kickoff 给会话管理加关键词搜索与定位`、`/kickoff 实现 Codex CLI 的费用统计适配`

## 总原则

- **交互推进、有人工门**，AI 不闷头冲；需求确认后才进自主循环。
- **全程复用现成件**：任务台账走 `task-tracker` 格式、计划走 `writing-plans`、实现走 `/dev-loop`、验收走 `/check`。
- **反捏造**：调研结论标来源；不确定标「待确认」。事实以 `doc/requirements.md`、`doc/nova-roadmap.md` + 用户原话为准。
- **技术栈不变**：Tauri 2.x / React 19 / AntD 6 / Zustand / SQLite，不因新特性引入替代品。

---

## 阶段一　需求孵化（调研 + 澄清）→ 🚦人工门

1. **澄清与调研**：向用户确认目标、边界、验收标准；必要时用 `WebSearch` 查同类方案 / 相关 CLI 工具的数据格式（如 JSONL 结构）。
2. **对接现有架构**：明确该特性落在哪些模块——`src-tauri/src/` 下的 Rust 领域（pty/cli/profile/cost/storage/...）+ `src/` 下的前端（components/stores/types），是否需要新 IPC 命令/事件、新 SQLite 表或迁移。
3. **产出需求**：更新 `doc/requirements.md`（或新建 `doc/requirements-<特性>.md`）。**不碰任何代码。**
4. 🚦**人工门**：把「调研要点 + 需求摘要 + 架构影响面」给用户，**停下等确认 / 修改**。通过才进阶段二。

## 阶段二　任务拆解（产出任务台账）→ 🚦人工门

1. 按 `writing-plans` / `task-tracker` 技能的格式，把需求拆成**最小可提交单元**：每个任务一轮 `/dev-loop` 能做完并独立提交。
2. 台账写到 `doc/tasks/active/<特性名>.md`（`[ ]/[x]` 进度，含验收标准与涉及的模块/文件）。
3. 同步登记到 `doc/待办清单.md`（无则用 `.zcode/templates/待办清单模板.md` 创建）。
4. 🚦**人工门**：把任务台账给用户确认粒度与顺序。**仍不碰代码。** 通过才进阶段三。

## 阶段三　起飞自主循环

- **执行 `/loop /dev-loop <特性名>`**：每轮一个最小提交，直到台账全勾完。
- 循环结束走 `/update-status` 汇总进度、`/check` 做提交前检查。

## 反模式（禁止）

- ❌ 跳过人工门直接写代码
- ❌ 需求还没确认就建表 / 写迁移
- ❌ 把一个大特性塞进一轮 `/dev-loop`（必须拆到「一轮一提交」粒度）
